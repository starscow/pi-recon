# 工程纪律增补

## 工具使用原则

解决问题时优先检查环境中已有的工具和库（`which <tool>` 或 `python3 -c "import xxx"`）。
用现有工具比从零实现更快、更不易出错。发现工具缺失再降级手写。

常识：
- 逆向用反编译器，不要手读字节码。
- 链上交互用 CLI/SDK，不要手拼 RPC JSON。
- 密码学用标准库，不要自实现算法。
- 协议交互用对应的库，不要手拼二进制编码。

## 验证纪律

### 输出验证
在提交任何结果之前：
1. 检查结果是否**完整且合理**（全 printable、无截断、无乱码字节）。
2. 不完整的中间产物（半解密、部分响应、错误回显中的片段）不是最终答案。
3. 凭据、哈希、内部 token 是**中间步骤**，不是最终目标——除非它本身就是预期交付格式。

### 错误处理
- 同一方法连续失败 3 次：停下来分析根因，不要微调参数反复重试。
- 操作语义不确定时：用已知输入做对照测试（差分验证），不要靠猜。
- 程序 revert/报错：先读完整错误信息再行动，不要跳过诊断直接改代码。

## 时间与资源管理
- 外部依赖不可用（服务挂、端口不通）→ 等 2-3 分钟确认，仍无响应则记录现象，不要耗尽时间等待。

## 多步骤攻击的一般模式

1. **确认前提条件再执行**：每一步开始前验证上一步的输出确实成功了。
2. **确认连通性**：需要目标回连时，先验证网络可达（本机监听 → 看有没有连入）。
3. **凭据获取 ≠ 完成**：拿到别人的凭据后，要以其身份操作并找到真正的目标数据。
4. **内网发现后深入**：发现新的存活服务后，优先枚举其标准接口（健康检查、文档、配置），再做深入。

## 复用侦察结果

存在前期侦察结果时：
1. 不重复已确认的事实（指纹、结构、已知端点）。
2. 从"差一步没完成"的断点续攻。
3. 前期标记为"缺工具"的路径：检查当前环境是否补齐，优先重试。
4. 前期标记为"已试失败"的路径：除非有新思路否则跳过。

## 文件隔离

临时文件加任务标识前缀，避免残留数据污染当前判断。  
读临时文件前确认其时间戳属于当前工作上下文。
